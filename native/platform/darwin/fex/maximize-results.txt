What is established: compilation does not account for the observed stalled
browser intervals. There is substantial host API/service work and unnecessary
translation-cache invalidation. A late DXMT endpoint does not locate all of its
upstream delay in the GPU process. The existing warm-cache experiment also did
not remove the multi-second first-maximize tail. Do not enable the cache by
default on this evidence.

What is not established: an exhaustive per-guest-thread critical path, exact
Chromium lock/IPC ownership, or a universal cause of both historical stalls.
Stack sampling is statistical, native workers overlap, and compile counters
include elapsed time in CompileBlock (not pure compiler CPU). Page-fault counts
are recorded but do not establish fault latency. Lazy DLL load, scheduling,
handle-channel polling, and guest work remain possible contributors. No claim
that all unidentified stacks are translated execution.

Experiment: private non-executable x64 data writes bypass NotifyMemoryDirty.
The original path walks every thread's translation cache even for API outputs
on ordinary stacks. Executable pages, image mappings, shared mappings, WoW64,
and unrecognized/cross-region ranges retain the original notification. Protection
transitions still notify FEX. No new sleep, throttling, cache default, scheduler
policy, or resize behavior. Production changes are Mac-only.

Measurement: private worktree build; nice 10, two jobs, prebuilt components
unchanged. Control-file reads limited to ten per second. Time starts when the
probe consumes and posts WM_SYSCOMMAND; external write times are in runner logs.

This explains part of the steady-state cost as continuing host/guest execution
and, in one renderer, translation; it does not assign every millisecond to an
API or a wait. The earlier software sample's 170/164/209 ms split is not a new
measurement of this build. These overlapping per-process intervals must not be
summed or subtracted into an exact running/compiling/waiting decomposition.
Sampled worker waits are FexWorker condition variables and controller waits
are host event/poll waits. Which guest lock/message/IPC dependency prevents
progress while those workers wait is not established. In particular, the
unaltered parallel scheduler has not been exonerated by this investigation.

Scope and next work:
  Production diff is exclusively native/platform/darwin/fex: fex_process.cpp,
  fex_process_test.cpp, parity.cmake, and this report. Temporary shared-code
  probes are removed; no production native/desktop or native/nt edits.
  The private-write guard avoids a proven unnecessary path; it does not establish
  that invalidation was the dominant cause. Its correctness depends on existing
  protection notifications invalidating code before it can execute again.
  Shared mappings are explicitly marked so aliases retain notification behavior.
  Remaining candidate: very frequent QPC API exits amplify handle-channel polling
  and host API work. native/nt/providers.cpp deliberately disables the guest QPC
  prelude for FEX because guest RDTSC scaling differs from Darwin CNTVCT.
  A future fast path needs calibration of FEX's actual guest clock and clock
  correctness tests; blindly enabling the existing calibration is unsafe.
  Event-driven handle-channel service is another candidate requiring attribution
  and upstream coordination, not a reason to rewrite shared code in this patch.
  Need a second reserved machine window to trace the remaining critical guest
  thread/IPC dependency and measure the signed-in Steam main window. Do not
  overrun the current 15:30 deadline or assume code-cache defaults solve this.
