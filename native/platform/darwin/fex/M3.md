# M3: resident parallel FEX guest workers

Engineering x64 thread backend on `t3/fex-parallel-threads`, based on the M2a
merge `9a3151114f071cb8ba703b654206b4aaf4d02991`. Nothing pushed. Rosetta remains
the default; `RAVEN_FEX_MODHOST` defaults OFF. With the opt-in FEX build,
`--execution=fex` retains cooperative scheduling by default; set
`RAVEN_PARALLEL=1` for one resident host thread per Windows guest thread.
This follows the cooperative-default/parallel-option policy in the design's M3.
No entitlement, Tier 1, system setting or debugger work was performed.

## Design

The existing `NativeThreads` scheduler still owns the NT/API coroutine frames,
wait predicates, APC queues, guest thread objects, TEBs, DLL/TLS notifications,
suspend counts and exit codes. NT/API handlers execute on the controller thread.
Guest instructions execute on distinct resident `std::thread`/pthread workers,
including the main guest. While a controller coroutine waits for its worker's
stop, `set_execution_wait` lets the existing scheduler run other guest threads.
A process eventfd wakes its descriptor-based wait path. No new NT scheduler or
parallel mutation of Raven's NT object tables is introduced.

Each worker constructs a private module ThreadEnvironment, installs module TLS,
calls the real exported `ThreadInit`, and owns its AMD64 context/CHPE CPU area,
emulator stack, call-return stack, translated state and alternate signal stack.
The Windows guest TEB's CPU-area pointer references that worker's CPU area; its
GS address and guest thread ID continue to come from NativeEnvironment. The
module's private TEB retains its actual host thread identity for initialization,
imports and termination. Process initialization retains the original controller
module thread for memory notification/import calls.

Dispatch/fault stop packets, sigjmp targets, execution TEBs and JIT protection
state are per host thread. Signal dispositions are installed once for the process;
workers install only their alternate stacks. A stopped worker publishes its
packet with release ordering before waking the controller. Context reads/writes
reject a running selected worker. `save_thread(false)` leaves packet ownership
with its worker; explicit paused snapshots permit context edits.

Remote suspension sets the worker's FEX doorbell, waits for the stop, and takes a
snapshot. Resumption applies edited context before restarting. The interrupted
controller execution frame consumes this internal doorbell and continues within
its original deadline. Nested suspend counts, waits and APC/alertable delivery
use the existing NT implementations. The Darwin-only `SetThreadContext` handler
is registered through a small shared thread-API seam only when FEX is selected;
it supports x64 control/integer groups, preserves other context, and rejects
unsupported groups and an unsuspended remote thread. Existing GetThreadContext
provides the control/integer snapshot. This is not full XSTATE context support.

Parallel providers normally replace served stubs with a GS-based protocol. FEX
validates those exact canonical bytes and routes them directly to their existing
API traps; it does not advertise served or queued graphics support. Cooperative
FEX retains M2's null-pointer fallback. Protection/release notifications now
bracket the actual host mapping mutation under the module's tracker protocol.

Reaping or terminating a noncurrent guest stops and joins its worker before its
TEB and stack are unmapped. Workers call the real `ThreadTerm(-2, 0)` on their
own host thread/private TEB, then release their environment. Controller teardown
joins every remaining worker before removing signal handlers, wake descriptors
or guest mappings. ThreadTerm failures fail the operation; destructor failures
abort with a diagnostic instead of reporting guest success. The original
process-lifetime retained module/reinitialization limitation is unchanged.

## Qualification

All builds use `-j8`; all CTest runs use `/tmp/raven-ctest-lock.sh`. Only area
selections were run. The external patch-12 module remains unchanged:
SHA256 `9f1dc47f38fb51df2ff41353410793aa5c69f988d56831037ce0f3db45db25aa`.
No new FEX source patch or DLL rebuild is required: its existing ThreadInit,
ThreadTerm and suspend doorbell exports provide the lifecycle.

New guest fixtures run with `RAVEN_PARALLEL=1;RAVEN_SLICE_MS=0`:

- contention: two workers cross a barrier without API calls, then execute
  200,000 atomic increments with an exact final count and distinct checked exits;
- context: suspend a computing worker, get/set/read back R12, nest suspend counts,
  verify it cannot exit while suspended, then verify the running guest sees R12;
- worker SEH: real write AV and software RaiseException handled on a worker;
- APC: an alertable worker receives a callback with its own Windows thread ID;
- lifecycle: 64 pairs of normal returns and ExitThread exits, suspended starts,
  repeated reaping, and termination of a computing worker with checked exit code;
- unhandled worker exception: full NT exit-code channel/host exit qualification;
- unchanged kernel-threads fixture: existing waits, critical sections, TLS,
  SRW/condition variables, synchronization and APC contracts under parallel FEX.

Parallel engine variants additionally exercise the infinite-loop deadline with
context repair/resume, and executable code modification/invalidation.
The strict process runner requires both host exit and guest return/status; no new
WILL_FAIL tests. Missing modules still produce explicit skip 77.

Final provisioned area result: **108/108 FEX tests passed**, no skips,
including **9 M3 tests**. The seven guest/scheduler tests also passed ten
consecutive runs each (**70 executions**). Shared/Rosetta regression selection:
**25/25 passed**. After clearing a potentially stale event in the termination
fixture, its focused rerun passed **1/1**. This is a subset rerun, not another
distinct contract. Complete test output is retained in `m3-evidence.json`.
Intermediate failures are recorded there as failures, not passing evidence.

## Performance and remaining scope

No compute, Firefox latency, audio deadline or representative application
benchmark was collected. CTest elapsed times are test evidence, not throughput
measurements. Parallel execution avoids the cooperative path's per-resume timer
thread, but uses condition-variable handoffs for each stop. API handlers remain
serialized on the controller. Software TSO and Tier 0 protection policy remain;
no performance improvement or default-switch conclusion is inferred.

Known inherited limits include signal async-safety (FEX signal callbacks may
allocate/lock), general native unwind/exception cleanup, full AVX/YMM state,
coarse 16 KiB guest protection and unsupported PAGE_GUARD. SetThreadContext is
control/integer only; unsuspended remote context manipulation, debug registers,
full NT context API parity and cross-process thread context are not qualified.
Queued/served graphics and native unix-library/audio callback integration remain
unsupported; the worker APC test qualifies nested guest callbacks, not those
native library integrations. Broader memory/SMC races and production workloads
remain qualification work. The test suite proves concurrent guest instruction
progress, not general Windows or application parity.

WoW64 was not started. The design's M4 describes a direct FEXCore guest-window
integration, while the decided module-host path's RavenHost frontend is compiled
only into ARM64EC. RAVENHOST.md explicitly leaves the WoW64 dispatch/context and
guest-window protocol unimplemented; M2.md also defers that contract. A concrete
xtajit.dll host-table/entry/context/exception protocol and 32-bit address audit
are needed to scope that next module milestone. This handoff leaves those design
choices for review instead of inferring them from passing x64 thread tests.
