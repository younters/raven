Software TSO
------------
Raven does not override the pinned frontend's memory-model defaults:
TSOEnabled=true, VectorTSOEnabled=false, MemcpySetTSOEnabled=false,
HalfBarrierTSOEnabled=true, StrictInProcessSplitLocks=false,
KernelUnalignedAtomicBackpatching=true, VolatileMetadata=true.
The Windows frontend attempts hardware TSO through FEXUnixLib; Raven returns
unavailable, retaining software TSO. No paranoid or auto-migration setting was
found in this pin. UpdateAtomicTSOEmulationConfig only checks hardware support
and scalar/vector/REP flags; it has no per-page shared/private or live-thread
classification. Do not assume RAVEN_PARALLEL=0 makes a Windows process
single-threaded or unable to access memory shared with another process.
Already-relaxed vector/REP defaults match upstream Linux FEX and its Windows
ARM64EC frontend. No further relaxation shipped and no per-option differential
cost was measured. Globally disabling scalar TSO would violate this workload's
correctness requirements.

Cross-process cache: measured, NOT implemented
--------------------------------------------
Across 17 exiting FEX processes: 8,535,720 compilation attempts (see JSON for
exact counts) and 73.029 seconds aggregate compilation time. These overlap;
never subtract their sum from browser wall time. Largest process: 3,868,993
attempts / 32.854 seconds. Others ranged 0.359 to 15.136 seconds. The timer
includes repeated translations; it does not distinguish DLL compilation from
anonymous/V8 code and therefore is NOT an estimate of recoverable cache savings.

Two distinct upstream mechanisms exist:
1. EnableCodeCachingWIP/AOT: Windows ImageTracker loads offline-generated
   caches; it does not save a live process's mixed JIT buffers. LoadAOTImages
   still uses CodeCacheConfigId=0 (TODO). SaveData serializes a whole current
   code buffer/lookup map and relocates it in place; it is not a safe module
   cache writer to call on an active multithreaded process. LoadCache also
   copies its header before establishing a full external-file bounds contract.
2. DiskCache: real per-block fossilize databases, config/host-feature buckets,
   guest-byte hashes, relocation-aware backend loading and file locks exist.
   This is the better starting point; it is not inherently impossible on Tier 0.

Raven's map_image currently uses NotifyMemoryAlloc/protect, not the frontend's
HandleImageMap/NotifyMapViewOfSection path. Its ImageTracker is consequently not
populated with guest DLL identity/section information for LookupExecutableFileSection.
The frontend's PE helper RtlImageNtHeader is also restricted to the FEX module
in RavenNT::image_nt_header. Merely enabling DiskCache would route guest DLLs
through anonymous caching, not the requested module-hash/config/build contract.
The Windows image FileId is based on basename, timestamp and image size, not a
cryptographic module hash. Existing machine/process buckets do not themselves
provide a Raven patched-build identity. A production integration needs:
- validated registration/unregistration of loaded guest image sections and a
  content-hash identity, including provider-modified image bytes;
- an explicit patched-module/build namespace around config/host-feature keys;
- validated NT file/mapping/locking paths, bounded file parsing, concurrent
  publication and corrupt-cache recovery; same-root cross-process hit evidence;
- ASLR, unload/reload and configuration-mismatch tests on the actual cached path.
I did not ship an unvalidated cache or claim this area complete. The missing
integration is substantial but feasible future work. Translation merits priority;
the present counters justify further investigation but do not prove all of its
cost is cross-process DLL retranslation. Multiblock and V8/SMC changes remain
with the other agent; patches 0040-0049 were not touched.
