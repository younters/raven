FEX translation retention: implementation and qualification
==========================================================
Base: perf/fex-chrome-call-costs / 8d6d8690.
Branch: perf/fex-retranslation. Implementation HEAD: bf8a323494434ced1061fbdf81669efd3423d493.
Final evidence-only commit is reported in the handback.

Result
------
Confirmed two local problems, fixed with patch 0061:
* An executable protection notification invalidated translations even when an
  entirely RX interval stayed RX and its bytes could not have changed.
* RWXIntervals retained pages after RWX -> RX. Raven initially registers an
  entire image as RWX, then applies section protections; consequently immutable
  DLL code retained writable-code status. Darwin's frontend generates inline
  SMC validation for writable code because it cannot trap logical 4 KiB writes
  with physical 16 KiB permissions. Removing stale RWX membership removes this
  unnecessary validation and associated compilation/code-buffer pressure.
The relative contributions of these mechanisms were NOT isolated experimentally.

All normal invalidation paths inspected already use 4 KiB FEX guest pages.
No evidence of blanket 16 KiB invalidation or ordinary range invalidation
clearing every lookup translation was found. Full code-buffer clears are
separately profiled. Current upstream InvalidationTracker had the same behavior;
no newer applicable invalidation fix was found to backport. See README links.

Retain invalidation for writable transitions, execute-right changes, real dirty
notifications, code writes, explicit flushes, frees and faults. Empty non-null
flush ranges do nothing; NULL retains whole-process flush semantics. Forward
FlushInstructionCache/NtFlushInstructionCache to the Windows frontend, matching
Wine ARM64EC. Accept both pseudo-handles and real SelfProcessObject handles.
Cross-process flush notification remains unsupported rather than returning a
false local success for a foreign handle.

Parent follow-up: deterministic x32 compiler failure resolved
----------------------------------------------------------
The diagnostic run with RAVEN_TRACE_X86=1 and RAVEN_TRACE_FAIL=1 showed:
  LoadLibraryW("d3dcompiler_47.dll")
  cannot load d3dcompiler_47.dll: PE preferred base is unavailable and image
  has no relocation table
The client never reached GetProcAddress or a FlushInstructionCache API.

The fixture built here had image base 0x70040000 and relocation directory (0,0).
The passing reference build's same fixture had base 0x6bdc0000, also no relocs.
MinGW's default DLL image base depends on its output path; this worktree's build
path placed the DLL in the native x86 API-provider region starting 0x70000000.

fixture-placement difference, not a compiler lookup flake or flush-path failure.

fixture an explicit 0x30000000 image base. Its existing native app-local compiler
regression remains, checking the DLL's actual D3DCompile return value. The 64-bit
fixture and runtime/flush/handle/API-registration code are unchanged.

B. Valid remote ProcessObject handles now succeed for Win32 and NT flushes.
Real self handles still forward locally, and invalid handles still fail with
ERROR_INVALID_HANDLE / STATUS_INVALID_HANDLE. Local unmapped, overflowing and
partially mapped ranges are clipped to actual mapped guest pages before any
WoW64 host-pointer conversion; no arbitrary unmapped address is dereferenced.
Remote writes already invoke the target's write_memory notification, so a
standalone remote-flush transport was not added.

Aliased and cross-process section writes were NOT correctly covered by the
original RX-retention optimization: a different virtual address's write cannot
be observed through the RX mapping's own permissions or dirty notifications.
Patch 0063 registers shared mappings in a separate SharedIntervals tracker.
QueryExecutableRange requests FEX's existing Darwin inline byte validation for
executable shared views. Changed bytes discard the stale block before execution,
including writes through an RW alias and ordinary stores from another process.
Sharedness is cleared on free/unmap. It does not change logical protection,
place RX pages in RWXIntervals, or enable write-fault recovery for an RX view.
Private/image RX mappings keep their optimized behavior.

Coverage:
* Eight guest cases: x32/x64, explicit-flush/no-flush, serial/parallel. Each
  maps one section RW and RX, modifies bytes through RW, executes through RX,
  then has a child modify that section and executes again. Covers real self and
  suspended-child handles, both flush APIs, invalid handles and arbitrary ranges.
* Two backend flush-only cases: mutate the loader's backing alias directly,
  with no protection/dirty notifications. The old translation must remain before
  the explicit flush (negative control), and the new bytes must execute after.
* Two guest API forwarding cases: unchanged private RX code must compile again
  after FlushInstructionCache through OpenProcess(current pid). Without the
  forwarding the count assertion fails. Expected code page: unique=1,
  repeated=2, recompiled=1 (one rewrite plus one explicit unchanged-byte flush).
